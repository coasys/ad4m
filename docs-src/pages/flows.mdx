# Flows

A flow is a state machine that a group advances together, over an expression that lives in a shared Perspective.

Unlike a status field, which holds whatever the last writer assigned, a flow's state is produced by the group's own rules. Every transition is backed by an on-graph `FlowTransitionProposal`, optionally gated by a `ConsensusRule` specifying how many distinct agents must sign before it counts. Each replica recomputes the state independently from links it can verify.

Flow definitions are [Social DNA](/social-dna): a flow is data in the Perspective, shared like any other link. Two agents in a [Neighbourhood](/neighbourhoods) run the same flow because they hold the same definition, not because they run the same app.

## State is derived, not stored

A flow's state is derived on every read, from the signed links present at that moment. To answer "what state is this task in?", the engine:

1. starts at the flow's first state,
2. looks at the declared edges out of it,
3. takes whichever edge collected enough distinct, eligible signatures earliest,
4. repeats from the state that edge leads to,
5. stops at the first state where no edge has reached quorum. That state is the result.

This has three consequences:

- **Replicas converge without coordination.** Same links in, same state out. Every choice in the walk is made by an explicit sort key, not by the order a database returned rows.
- **The derivation is independently verifiable.** It is a pure function over plain data, requiring no network and no database. Given the links, a third party can re-run it and confirm or refute a claimed state.
- **Retracting a vote moves the flow back.** Withdrawing a signature that settled an edge returns the flow to its prior state. This follows from deriving state rather than storing it, and is what makes independent verification possible. See [Reject is not cancel](#reject-is-not-cancel).

<Callout type="info" emoji="ℹ️">
  The engine does write a `currentState` value onto each flow instance, but it
  is a cache for readers rather than an authority. See [The `currentState`
  cache](#the-currentstate-cache). Nothing in the derivation reads it.
</Callout>

## The on-graph objects

Four things make up a flow, and all four are ordinary links in the Perspective.

### `SHACLFlow` — the definition

The flow itself: a name, a namespace, the states, the transitions between them, and the English that tells an LLM what the states mean. Registered with `perspective.addFlow(name, flow)`, which serialises it to links and records it under `ad4m://self --ad4m://has_flow--> "name"`.

Its canonical identity is `flowUri`, formed as `${namespace}${name}Flow`, e.g. `delivery://DeliveryFlow`. Instances store that URI rather than the bare name, because bare names collide when two communities share social DNA.

| member | meaning |
| --- | --- |
| `inputTypes: string[]` | subject-class URIs the flow accepts as its base expression. Empty, or containing the `"any"` wildcard, matches anything. |
| `outputTypes: string[]` | subject-class URIs a completed run is expected to have produced. |
| `interpretationHint?: string` | one-paragraph English frame for the whole flow. |
| `creationHint?: string` | when an instance of this flow should be *started* (as opposed to advanced). |
| `context?: ModelQuery[]` | background queries threaded into the LLM prompt as context — never as evidence. |
| `consensusRule?: ConsensusRule` | default rule for transitions that don't override it. |
| `states` / `transitions` | added with `addState()` / `addTransition()`. |

### `FlowState` — one state

```typescript
interface FlowState {
  name: string;                  // "Scoped"
  value: number;                 // ordering key; lowest value is the initial state
  interpretationHint?: string;   // what puts an instance IN this state (see below)
  requires?: ModelQuery[];       // model-level guard, AND semantics
  semanticCheck?: string;        // optional LLM confirmation after `requires` matches
  consensusRule?: ConsensusRule; // per-state override of the flow-level default
}
```

`value` is an ordering key, not a progress percentage: `0, 1, 2` and `0, 10, 20` behave identically. The lowest-valued state is where every instance begins.

`requires` defines a state's entry condition in terms of graph contents rather than a user action. Each `ModelQuery` names a subject class, optional per-property conditions, a cardinality, and optionally an anchor (`linkedTo: "base"` or `"flow"`). All queries in the array must match.

### `FlowTransition` — one edge

```typescript
interface FlowTransition {
  actionName: string;   // "Scope" — the label a UI shows
  fromState: string;
  toState: string;
  actions: AD4MAction[]; // link mutations to perform alongside the transition
}
```

### `FlowInstance` — one run

When a flow is started on a concrete expression, an instance node is minted. On the graph it is the hard-wired subject class `FlowInstance` (`ad4m://FlowInstance`); in TypeScript the raw `@Model` row is exported as **`FlowInstanceRecord`**, because the name `FlowInstance` is taken by the wrapper class you actually work with.

| predicate | field | notes |
| --- | --- | --- |
| `ad4m://flow/flow_uri` | `flowUri` | which `SHACLFlow` this runs; the row's identity |
| `ad4m://flow/base` | `subject` | the expression the flow rides on |
| `ad4m://flow/current_state` | `currentState` | `Local` link; this replica's cache, not an authority |

### `FlowTransitionProposal` — one proposed move

One node per proposed transition, `ad4m://flow/proposal/<uuid>` when the engine mints it.

| predicate | field | notes |
| --- | --- | --- |
| `ad4m://flow/instance` | `flowInstance` | the instance this targets; the row's identity |
| `ad4m://flow/from_state` | `fromState` | |
| `ad4m://flow/to_state` | `toState` | |
| `ad4m://flow/proposer` | `proposer` | DID that opened it |
| `ad4m://flow/evidence` | `evidence[]` | URIs cited as satisfying `toState.requires` |
| `ad4m://flow/evidence_hashes` | `evidenceHashes` | JSON `{ uri: sha256 }`, sealed at mint |
| `ad4m://flow/run_uri` | `runUri?` | the `InterpretationRun` that produced it, when an LLM pass did |
| `ad4m://flow/rationale` | `rationale?` | free-form justification |

Two more predicates belong to the proposal but are not fields of the class:

- `ad4m://acceptedBy` → a DID is a vote. There is no separate Vote class; a signed link carries the same information.
- `ad4m://flow/resolved_as` → `"fired"` is a history mark for UIs, written `Local`. It is not an input to the derivation.

<Callout type="warning" emoji="⚠️">
  Every field of a proposal is read only from links the proposer signed, and
  only when the executor recorded the signature as valid. A synced link
  claiming to belong to a proposal but signed by a different agent is invisible
  to the engine, and a proposer who published two different values for one
  field invalidates their own proposal. No part of this path uses
  last-write-wins.
</Callout>

## `interpretationHint`, and how the LLM sees it

Each state's `interpretationHint` is one English sentence. It is not a code comment: the interpretation engine renders it into the prompt handed to the LLM, next to that state's guards, so an agent evaluating a transition works from the group's stated meaning of the state rather than inferring it from the name. Vague hints produce correspondingly vague agent proposals.

When an extraction pass runs on a scope that has live flow instances, the prompt gains an `active_flows` array — one entry per instance:

```json
{
  "instance": "ad4m://flow/instance/7f3a…",
  "subject": "ad4m://task/1",
  "flow": "Delivery",
  "currentState": "Identified",
  "tokens": {
    "$flow.base": "ad4m://task/1",
    "$flow.instance": "ad4m://flow/instance/7f3a…",
    "$flow.uri": "ad4m://flow/instance/7f3a…",
    "$did": "(acting DID - substituted at evaluation time)"
  },
  "hint": "Advance a Task through delivery: Identified → Scoped → …",
  "consensus": "2 signers",
  "nextStates": [
    {
      "name": "Scoped",
      "hint": "The Task has an acceptance criterion.",
      "requires": "at least 1 match of AcceptanceCriterion linked to the base",
      "semanticCheck": "The scope was agreed on, not merely discussed.",
      "consensus": "2 signers"
    }
  ]
}
```

Three properties of that block:

- Optional fields are omitted when unset, so a flow costs prompt tokens in proportion to what it declares. When no flows are live the key is absent entirely, so the LLM is not shown empty flow scaffolding.
- `requires` is rendered to English rather than raw query JSON. The `$flow.*` tokens are preserved verbatim, with the `tokens` legend giving their resolved values for this instance; the engine substitutes them after the model returns.
- A [contested](#contention) flow is flagged as stalled, so the model does not read it as awaiting votes.

### Which component writes the proposal

Proposals are minted by a deterministic evaluator, not by the LLM.

After an extraction pass commits its writes, the evaluator checks every live instance against the `requires` guards of the states reachable from its current one. Each fully satisfied `(instance, next-state)` pair becomes a `FlowTransitionProposal`, with the matched instances as its evidence bag and an order-independent SHA-256 over their canonicalised content as the seal. This advances a flow in the case where the LLM produced the evidence for a transition but did not propose it.

LLM-authored proposals, whether from the strategy path's JSON output or from the `{FlowName}_propose_transition` tool the harness exposes, do not fire a transition on their own. Where one names a transition the deterministic guard has already satisfied, its `reason` becomes that proposal's `rationale`. Otherwise it is dropped.

Between guard and write sits one optional gate: a state carrying a `semanticCheck` hint triggers a second, smaller LLM call asking whether the condition holds. An affirmative answer lets the proposal through. A negative answer, an unclear answer, and an LLM error all discard the transition, so an uncertain confirmation does not advance a flow.

## The read surface

```typescript
import { FlowInstance, SHACLFlow } from "@coasys/ad4m";

// Every flow registered on this perspective, by name.
const names = await perspective.sdnaFlows();            // ["Delivery"]

// Which of them accept this expression? Matches the expression's registered
// subject classes against each flow's `inputTypes`.
const available = await perspective.availableFlows("ad4m://task/1"); // ["Delivery"]

// Load a definition back.
const flow: SHACLFlow | null = await perspective.getFlow("Delivery");

// Mint a run, seeded in the flow's lowest-valued state.
const instance = await FlowInstance.start(perspective, "Delivery", "ad4m://task/1");

// Enumerate runs. The filter is a flow name, or `{ flowName?, subject? }` —
// pass `subject` to ask "what is running on this expression?".
const all       = await FlowInstance.findAll(perspective);
const deliveries = await FlowInstance.findAll(perspective, "Delivery");
const onThisTask = await FlowInstance.findAll(perspective, { subject: "ad4m://task/1" });
```

On a `FlowInstance` wrapper:

| member | type | |
| --- | --- | --- |
| `uri` | `string` | the instance node's URI — what proposals reference |
| `subject` | `string` | the base expression |
| `flowName` / `flowUri` | `string` | display name / canonical identity |
| `currentStateName` | `string` | state name |
| `currentState` | `FlowState` | the state object on the definition — hint and guards included |
| `availableTransitions` | `FlowTransition[]` | edges leaving `currentStateName`; empty on a terminal state |
| `startedAtMillis` | `number \| undefined` | from `Ad4mModel`'s synthesised `createdAt` |
| `proposals()` | `Promise<FlowTransitionProposal[]>` | every proposal targeting this instance |
| `shape` / `record` | `SHACLFlow` / `FlowInstanceRecord` | the two wrapped objects, if you need to reach past the wrapper |

```typescript
instance.currentStateName;                     // "Identified"
instance.currentState.interpretationHint;      // the sentence the LLM was given

for (const t of instance.availableTransitions) {
  console.log(t.actionName, "→", t.toState);   // "Scope" → "Scoped"
}

const pending = await instance.proposals();
```

<Callout type="info" emoji="ℹ️">
  `findAll` never registers classes. On a perspective that has never minted an
  instance it returns `[]` rather than installing the shape — a read must not
  sync a write to every peer in the neighbourhood. Registration happens in
  `FlowInstance.start`, which is the write path.
</Callout>

## The write surface: accept and reject

Two methods make up the whole flow-writing API currently available to an app.

```typescript
// Add my signature to a proposal, then re-derive.
// Returns every transition that fired as a result.
const fired: FlowFireOutcome[] = await instance.acceptProposal(proposal);

// Withdraw my own links from a proposal. Returns how many went.
const retracted: number = await instance.rejectProposal(proposal);
```

Both accept either a `FlowTransitionProposal` or its URI. The same pair is reachable over WS-RPC as `perspective.acceptFlowProposal` / `perspective.rejectFlowProposal`, and over MCP as the `flow_proposal_accept` / `flow_proposal_reject` tools.

A fired transition is reported as:

```typescript
interface FlowFireOutcome {
  instanceUri: string;
  fromState: string;
  toState: string;
  voters: string[];                   // the distinct DIDs that settled the edge
  contributingProposalUris: string[]; // every proposal that fed it — twins included
}
```

An empty array is a normal result: a vote that has not yet reached quorum has still landed. More than one outcome occurs when a signature unblocks an edge that subsequent edges were already waiting behind.

### Verification happens at signing time

`acceptProposal` re-verifies the proposal's evidence seal against the signer's own copy of the graph before signing. If the cited content has changed since the mint, the replica declines to co-sign and writes nothing. It does not delete the proposal, because the local graph may simply be behind; deleting another agent's work on that basis would exceed a replica's authority. A replica can refuse only its own action.

Accept also refuses when the proposal is not engine-visible, and when it leaves a state the flow no longer occupies.

Consequently the derivation re-runs no guards. Every vote it counts was cast by an agent that checked the seal first, and settled history is not re-tested against the live graph. Re-testing would mean that editing a task cited by a completed transition silently unwound the flow that consumed it.

### Reject is not cancel

<Callout type="warning" emoji="⚠️">
  `rejectProposal` withdraws only the links the calling DID signed. It does not
  cancel another agent's proposal.

  It deletes that DID's vote, or its whole proposal if it opened one, and
  returns the number of links removed: one for a withdrawn vote, more when
  retracting an opened proposal. It does not touch another agent's links, and
  if the caller signed nothing on the proposal it returns an error rather than
  silently doing nothing. A link that names a DID but carries a different
  agent's signature is not retractable by that DID.

  Because state is recomputed from the links present at read time, withdrawing
  a vote that had settled an edge returns the flow to its prior state. With the
  vote removed the edge is one short of quorum, so the walk stops earlier.
  There is no "already fired" guard: the `resolved_as → "fired"` mark is an
  index rather than authority, and guarding on it would contradict deriving
  state from current links.
</Callout>

### Not implemented

The following are absent rather than stubbed:

| | |
| --- | --- |
| `FlowInstance.proposeTransition()` | no client-side propose API — proposals come from the engine's evaluator pass (above) |
| `FlowInstance.fireAction()` | no direct fire — an edge fires only by reaching quorum |
| `onStateChange` / `onProposalAdded` / `onProposalResolved` | no flow subscriptions — poll `findAll` / `proposals()` |

They are scheduled for the manual-proposal and subscription-topic slices. Until then, an app's write surface is accept and reject.

## A transition, end to end

Alice and Bob share a Neighbourhood. Their Delivery flow requires two distinct signatures to enter `Scoped`:

```typescript
import { SHACLFlow, FlowInstance } from "@coasys/ad4m";

const deliveryFlow = new SHACLFlow("Delivery", "delivery://");
deliveryFlow.inputTypes = ["ad4m://Task"];
deliveryFlow.interpretationHint =
  "Advance a Task through delivery: Identified → Scoped → InProgress → Review → Done.";

deliveryFlow.addState({
  name: "Identified",
  value: 0,
  interpretationHint: "The Task has been named but not yet scoped.",
});
deliveryFlow.addState({
  name: "Scoped",
  value: 1,
  interpretationHint: "The Task has an acceptance criterion.",
  requires: [{ className: "AcceptanceCriterion", linkedTo: "base", count: { min: 1 } }],
  consensusRule: { n: 2 },
});
deliveryFlow.addTransition({
  actionName: "Scope",
  fromState: "Identified",
  toState: "Scoped",
  actions: [],
});

await perspective.addFlow("Delivery", deliveryFlow);

// Alice starts a run on a task. It begins in the lowest-valued state.
const instance = await FlowInstance.start(perspective, "Delivery", "ad4m://task/1");
instance.currentStateName; // "Identified"
```

The conversation on that task then produces an acceptance criterion, an extraction pass writes it as an `AcceptanceCriterion` instance, and the evaluator finds `Scoped`'s guard satisfied:

```text
 ┌──────────────────────────────────────────────────────────────────────┐
 │ 1. PROPOSAL                                                          │
 │    Alice's evaluator pass writes ad4m://flow/proposal/abc,           │
 │    every link signed by Alice:                                       │
 │      flow/instance       → ad4m://flow/instance/7f3a…                │
 │      flow/from_state     → "Identified"                              │
 │      flow/to_state       → "Scoped"                                  │
 │      flow/proposer       → did:key:alice                             │
 │      flow/evidence       → ad4m://criterion/9 (the matched instance) │
 │      flow/evidence_hashes→ {"ad4m://criterion/9":"a91f…"}  ← the seal │
 │    The mint is Alice's own vote.                          [1 of n=2] │
 └────────────────────────────────┬─────────────────────────────────────┘
                                  │  sync
                                  ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ 2. VOTE                                                              │
 │    Bob calls instance.acceptProposal("ad4m://flow/proposal/abc").    │
 │    His replica recomputes the seal over ad4m://criterion/9 on ITS    │
 │    OWN graph first. Match ⇒ he signs:                                │
 │      ad4m://acceptedBy → did:key:bob     (signed by Bob)             │
 │    Mismatch ⇒ he declines and writes nothing.             [2 of n=2] │
 └────────────────────────────────┬─────────────────────────────────────┘
                                  │
                                  ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ 3. QUORUM — counted per EDGE, not per proposal                       │
 │    fold walks from "Identified":                                     │
 │      edge Identified→Scoped                                          │
 │        distinct eligible DIDs across ALL proposals for this edge     │
 │          = { did:key:alice, did:key:bob }  = 2                       │
 │        consensusRule for entry into "Scoped" = { n: 2 }              │
 │        ⇒ settled, at the 2nd voter's own timestamp                   │
 └────────────────────────────────┬─────────────────────────────────────┘
                                  │
                                  ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ 4. TRANSITION                                                        │
 │    The walk crosses the edge and stops in "Scoped" — no edge out of  │
 │    it has quorum. acceptProposal resolves to:                        │
 │      [{ instanceUri: "ad4m://flow/instance/7f3a…",                   │
 │         fromState: "Identified", toState: "Scoped",                  │
 │         voters: ["did:key:alice","did:key:bob"],                     │
 │         contributingProposalUris: ["ad4m://flow/proposal/abc"] }]     │
 │    The pass then writes Bob's Local currentState cache and a         │
 │    resolved_as → "fired" mark. Neither is ever read back.            │
 └──────────────────────────────────────────────────────────────────────┘
```

```typescript
const fired = await instance.acceptProposal("ad4m://flow/proposal/abc");
fired[0].toState;  // "Scoped"
fired[0].voters;   // ["did:key:alice", "did:key:bob"]
```

Now Bob changes his mind:

```typescript
const retracted = await instance.rejectProposal("ad4m://flow/proposal/abc"); // 1

const after = await FlowInstance.findAll(perspective, { subject: "ad4m://task/1" });
after[0].currentStateName; // "Identified" — back where it stood
```

One link was removed: Bob's `acceptedBy`. Alice's proposal is untouched and still stands. The edge is back to `1 < n = 2`, so the walk no longer crosses it and the flow returns to its prior state. No undo step ran; the same derivation executed over one link fewer.

### Why quorum is counted per edge

When two replicas mint proposals for the same transition concurrently, neither having seen the other's, the result is twin proposals for one edge. If quorum were counted per proposal, a flow with `n: 2` and two twins holding one vote each would remain at its initial state indefinitely, each one short.

The engine therefore asks whether the edge collected `n` distinct voters, counting across every proposal for that edge. Twins converge rather than deadlock, and both appear in the outcome's `contributingProposalUris`.

## Roles: who is allowed to sign

A `ConsensusRule` can require that voters hold a role:

```typescript
deliveryFlow.addState({
  name: "Done",
  value: 4,
  interpretationHint: "The Task is accepted and complete.",
  consensusRule: {
    n: 2,
    fromRole: {
      className: "Membership",
      where: { role: "reviewer" },
      didProperty: "agent",
    },
  },
});
```

`fromRole` is an ordinary `ModelQuery` over ordinary subject classes — roles are not a special kind of object, just data the flow points at. `didProperty` names the property on each match that holds the member's DID. (The alternative shape templates `$did` into `where` and treats a non-empty result as "this DID matches".)

Each vote is gated as of its own timestamp. A voter who held the role when signing still counts after the role is revoked, and a voter who signed before being granted the role does not count retroactively. Revocation is an explicit signed tombstone: it stops future votes rather than rewriting settled history.

A per-state `consensusRule` overrides the flow-level default, allowing early edges to require one signature while a final, irreversible edge requires two reviewers.

## Contention

If two edges out of the current state both reach quorum, the engine does not select a winner. It reports contention and the walk stops there.

Choosing by timestamp would adjudicate the race using values the racing agents supplied themselves. Rather than derive an authoritative result from untrusted input, the engine reports that the group disagreed, leaving resolution to the participants.

A contested flow is stalled rather than waiting: further votes cannot move it, because the obstruction is that two edges already hold a quorum. Any process that acts on a completed flow should refuse a contested derivation, and a UI should not render one as awaiting votes.

The result is three-valued:

| status | meaning |
| --- | --- |
| not contested | a fresh derivation ran and found no conflict |
| contested | two settled edges out of the current state |
| unknown | the state came from the cache, so contention was not computed; this asserts nothing either way |

`unknown` distinguishes a cache read from a computed result. It renders as nothing in the LLM prompt rather than as "no contention", because a representation that conflates "verified clear" with "never checked" fails in the permissive direction.

## The `currentState` cache

Each instance carries a `currentState` property so a reader who cannot afford a full derivation — a list view, a query filter, a prompt block — still sees an answer.

Two properties prevent it from becoming a competing source of truth:

- It is written as a `Local` link, so it never syncs. Each replica's cache is its own, and a peer's value can neither overwrite it nor be read as a shared claim.
- The derivation does not read it. The background pass updates it toward the derived state, in one direction only.

The history marks (`resolved_as → "fired"`) are `Local` for the same reason, with one additional consequence: the first pass a replica runs over an instance it has not previously derived performs a silent catch-up. It marks what has already settled and writes the cache without emitting outcomes, so joining a flow with existing history does not produce events for transitions that predate the replica.

The cache is suitable for display. Operations that act on flow state, including minting, voting, firing and any downstream payout, should derive it.

## Summary

A flow makes a group's process explicit, shared and checkable:

- Explicit: the meaning of a state is expressed in the data, as guards and an interpretation hint, rather than in application source or convention.
- Shared: the definition is Social DNA, so an agent joining the Neighbourhood receives the process along with the data, without installing the originating app.
- Checkable: state is derived from signed links, so each participant can verify a transition instead of trusting the application that displayed it.

Because the definition carries an English description for every state, the structure that drives a UI is the same structure an agent reasons over: one description of the process, serving both human and automated participants.
