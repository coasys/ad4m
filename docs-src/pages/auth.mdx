# Authentication & Capabilities

## Overview

AD4M uses a capability-based security model to protect user data and control access to agent functionality. Every application that wants to interact with an AD4M executor needs to request specific capabilities, which are then granted (or denied) by the user.

### What are Capabilities?

Capabilities in AD4M are like permission tokens that:

- Define what data an application can access (which perspectives)
- Specify what operations an application can perform
- Are scoped to specific domains and functions
- Can be revoked by the user at any time

A capability token might grant permissions like:

- Read access to specific perspectives
- Write access to create or modify links
- Ability to create new perspectives
- Permission to manage agent relationships
- Access to specific language functions

## Authentication Flow

### Standard Flow

When an application wants to connect to an AD4M executor, it goes through a secure authentication handshake:

1. The application requests access with specific capabilities
2. The AD4M executor generates a random verification code
3. The user must confirm the request and enter the code
4. Upon successful verification, a capability token is issued

This flow ensures that:

- The user explicitly approves application access
- The application only gets the permissions it needs
- The connection between UI and executor is secure

### Using @coasys/connect

A web app signs in with `@coasys/connect`. The person does not type a code: the library opens
the Coasys Connect frame on the auth domain (`https://coasys.id`, or `https://staging.coasys.id`),
where the person picks one of their own devices and the browser key signs the login.

```js
import { getAd4mConnect } from "@coasys/connect";

const { core, client } = getAd4mConnect({
  appId: "my-app", // the id the platform registry lists your origins under
  endpoints: { authDomain: "https://coasys.id" },
  capabilities: [{ with: { domain: "*", pointers: ["*"] }, can: ["*"] }],
});

core.addEventListener("authstatechange", (e) => console.log(e.detail));
const ad4m = await client; // an authenticated Ad4mClient
```

How it works:

1. The library makes a random `state` and a PKCE `codeVerifier`, and sends the frame the
   `state` and the SHA-256 `codeChallenge` (RFC 7636). The verifier stays in the page.
2. The frame signs a `user.loginWithKey` statement with the person's browser key. The
   executor checks that the page's origin is one of the app's origins in the platform
   registry, and answers the frame with a one-time **code** (60 seconds, one use), not a token.
3. The frame sends the code to the page. The page calls `user.redeemCode` with the code and
   the verifier. The executor gives the token only when the verifier matches the challenge.
4. The token (one hour) lives in memory only. The library renews it through the frame before
   it ends, and `core.disconnect()` ends the session.

A web grant is a normal app grant limited to the capabilities the app asked for. Only an app
the registry marks `firstParty`, on an identity that is the executor's operator, can hold the
operator role.

Old versions of `@coasys/ad4m-connect` kept the token in `localStorage`. `@coasys/connect`
removes those keys when it starts.

### Hosted multi-user nodes

On a hosted multi-user node an app can connect as a guest with `core.connectAsGuest(hostUrl)`.
The library makes a random account on the first visit and logs in with it afterwards. See
[Multi-User Mode](/multi-user) for accounts, DIDs and email verification. The token stays in
memory.

### Capability Specification

When requesting capabilities, you need to specify:

```js
{
  with: {
    domain: string | "*",     // Which perspective/domain
    pointers: string[] | "*"  // Which parts of the domain
  },
  can: string[] | "*"         // Which operations are allowed
}
```

Examples:

```js
// Request access to everything (development only)
{ with: { domain: "*", pointers: ["*"] }, can: ["*"] }

// Request read-only access to a specific perspective
{ with: { domain: "perspective-uuid", pointers: ["*"] }, can: ["read"] }

// Request specific operations on a domain
{ with: { domain: "friends", pointers: ["*"] }, can: ["read", "add", "remove"] }
```

### Admin Credential Override

For automated scenarios or system integration, the authentication handshake can be bypassed using an admin credential:

```js
// In your application
const client = new Ad4mClient({
  adminCredential: "your-secret-here",
});
```

This is particularly useful for:

- CI/CD pipelines
- Testing environments
- System services
- Management interfaces (the AD4M Launcher uses this internally)

The executor requires one: `ad4m-executor run` exits with an error when no admin credential (or an empty one) is set. Pass it through the environment, not the command line:

```bash
export AD4M_ADMIN_CREDENTIAL="your-secret-here"
ad4m-executor run
```

For tests and local development, `--insecure-no-admin-credential` (or `AD4M_INSECURE_NO_ADMIN_CREDENTIAL=true`) starts the executor without a credential; an empty token then has full admin access on a loopback-bound API, and is anonymous on a network-bound one (`--localhost false`, or TLS).

⚠️ **Security Note**: The admin credential grants full access to the executor. Use it carefully and never expose it in client-side code or public repositories.

## Best Practices

1. **Request Minimal Capabilities**
   - Only request permissions your app actually needs
   - Use specific domains and operations instead of wildcards
   - Consider read-only access when possible

2. **Handle Authentication States**
   - Check if capabilities are still valid
   - Implement reconnection logic
   - Handle capability revocation gracefully

3. **Secure Storage**
   - Store capability tokens securely
   - Never expose admin credentials
   - Implement token refresh mechanisms

4. **User Experience**
   - Clearly explain why your app needs certain capabilities
   - Provide feedback during the authentication process
   - Handle errors gracefully
