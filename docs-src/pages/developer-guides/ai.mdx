# AI in AD4M

<Callout type="info">
**Looking for AI agent integration?** This page covers running AI models *for* AD4M. If you want AI agents to *use* AD4M — creating perspectives, managing data, joining neighbourhoods — see the [MCP Server guide](/developer-guides/mcp).
</Callout>

AD4M gives applications language models, embeddings, speech-to-text and text-to-speech. The executor runs no model itself: it sends each request to a **model server**, on your machine (Ollama, llama-server, vLLM, speaches) or remote (OpenAI, Anthropic, any OpenAI-compatible API). It keeps the parts that are AD4M's: who may use which model, billing, AI tasks, the agent tool loop, transcription streams and their events.

## Overview

- An **endpoint** is one model server: a kind, a URL, an optional key, its capabilities (chat, embeddings, transcription, speech) and its health, checked every minute.
- A **model** is one model on an endpoint: a name, a type (`LLM`, `EMBEDDING`, `TRANSCRIPTION`, `SPEECH`), the endpoint, and the id the endpoint knows the model by (`remoteModel`).
- Each type has a **default** model. AI tasks, semantic dedup and the interpretation engine use the defaults unless told otherwise.
- `/v1/chat/completions`, `/v1/embeddings`, `/v1/audio/*` and `/v1/models` on the executor forward to the model's endpoint (OpenAI-compatible clients work against the executor unchanged).

A fresh executor has no models. Features that need one answer that no model is configured until one is added.

## Local AI on this device

The quickest setup needs no model server: the executor installs and runs one itself. The launcher's onboarding offers it first ("Set up local AI"), and WE's AI settings use the same calls.

1. **Detect.** `ai.localHardware` reads the OS, CPU, RAM, GPUs (NVIDIA through NVML, every other GPU through the Vulkan loader, AMD memory from sysfs, Apple Silicon's unified memory) and the backends a runtime can use: CUDA, Metal, Vulkan, ROCm (with the system ROCm libraries), CPU. It gives the device a hardware class (`apple-silicon-16`, `nvidia-12gb`, `amd-igpu-uma-128`, `cpu-8gb`, ...), by the AI wind tunnel's rules.
2. **Plan.** `ai.localPlan` picks, per service, the model the AI wind tunnel measured for that class (or the nearest smaller measured class: the family's smaller tiers, then the CPU classes), with the server flags it was measured with, and the runtime build for the best backend. On AMD, Vulkan replaces a recommended ROCm build: that build runs on the CPU, unannounced, without the system ROCm libraries. Chat runs without Qwen3.5's thinking (`--reasoning off`). The models run at once, so their memory adds up: it fits when the sum is at most min(GPU memory − 1 GB, RAM − 4 GB); when it does not, the largest model steps down. The plan says what it downloads, how much, and why it fits or not. `local_ai_device` (`cpu`, `cuda`, `metal`, `vulkan` or `rocm`; `--local-ai-device` / `AD4M_LOCAL_AI_DEVICE`) holds the plan to one backend: only its builds are used (the CPU build for a runtime with none for it), and the memory budget and the hardware class follow, so `cpu` plans by RAM on a machine with a GPU. The plan names the device it was held to (`device`).
3. **Install.** `ai.localInstall` downloads the pinned [llama.cpp](https://github.com/ggml-org/llama.cpp) `llama-server` and [NVIDIA NeMo-Speech.cpp](https://github.com/NVIDIA/NeMo-Speech.cpp) `nemo-speech` builds from their GitHub releases and the models from Hugging Face. Every file is checked against the sha256 the manifest pins before it is used (a file that changed upstream fails the install rather than running); an interrupted download resumes. Progress arrives as `ai-local-progress` events.
4. **Run.** The executor starts both servers as its own child processes on free `127.0.0.1` ports (never 9931 or 8080, the upstream defaults), each with a random API key, and restarts one that crashes (3 times, given back after 5 healthy minutes). llama-server serves chat and embeddings; nemo-speech serves transcription with NVIDIA's Parakeet TDT 0.6B v3 (25 European languages; it does not report the language it heard), on Vulkan on Linux where Vulkan runs, on Metal on a Mac, else on the CPU. After a start on a GPU build it checks the runtime holds GPU memory (`onGpu` in `ai.localStatus`; Linux with an AMD or Intel GPU). They stop with the executor and start with it again (`local_ai_autostart`).
5. **Register.** They appear as two endpoints, `This device (llama.cpp)` (chat and embeddings, llama-server in router mode) and `This device (NeMo Speech)` (transcription), marked `managed`, with their models as the defaults. The chat model takes tools as definitions (`nativeTools`): llama-server renders them with the model's chat template and parses the calls. A managed endpoint is not edited or removed with `ai.updateEndpoint` / `ai.removeEndpoint`: use `ai.localStop` / `ai.localRemove`. Its health is the supervisor's check (starting, stopped, failed), and once it runs, llama-server's liveness and nemo-speech's model listing.

```typescript
const plan = await ad4m.ai.localPlan();
console.log(plan.hardwareClass, plan.models.map((m) => m.modelId), plan.downloadBytes, plan.fits);

if (plan.fits) {
  const status = await ad4m.ai.localInstall({}, (p) =>
    console.log(p.phase, p.item, p.doneBytes, '/', p.totalBytes));
  console.log(status.runtimes.map((r) => `${r.provider}: ${r.phase} on ${r.port}`));
}

await ad4m.ai.localStop();         // the endpoints stay, down
await ad4m.ai.localStart();
await ad4m.ai.localRemove(false);  // true also deletes the downloaded files
```

| Method | Who | What |
|---|---|---|
| `ai.localHardware` | the main agent's sessions (AI READ) | this device |
| `ai.localPlan` | the main agent's sessions (AI READ) | what an install would do, and whether it fits |
| `ai.localStatus` | the main agent's sessions (AI READ) | what is installed, and each runtime's phase, port, restarts |
| `ai.localInstall` | the operator | download, start, register (long) |
| `ai.localStart`, `ai.localStop` | the operator | the runtimes |
| `ai.localRemove` | the operator | stop and unregister; `deleteFiles` also deletes the files |

**Storage.** Runtimes and models go to one per-user directory that every agent and app of the user shares, not into each agent's data: `~/.local/share/ad4m/local-ai` on Linux, `~/Library/Application Support/ad4m/local-ai` on macOS, `%LOCALAPPDATA%\ad4m\local-ai` on Windows (`local_ai_dir` / `--local-ai-dir` / `AD4M_LOCAL_AI_DIR` moves it). Each executor keeps only its own state (the chosen models, ports, pids and the runtimes' logs) in `<app data>/local-ai/`.

**Known gaps.** The models are chosen from the AI wind tunnel's measurements, and only measured hardware classes (and the classes they cover) get a plan. nemo-speech's Metal build is not yet measured on a Mac. There is no local text-to-speech yet.

## Setting up model servers

The launcher's onboarding (and Settings, AI) looks for model servers on this machine. Onboarding lists the chat models a server already serves first and preselects one, so a running server needs no download. It also offers the recommended models: a 4-8B instruct model that calls tools (`qwen3:8b`), an embedding model (`nomic-embed-text`) and, on a transcription server, `Systran/faster-whisper-small`. The SDK exports the list as `AI_RECOMMENDED_MODELS`.

| Server | Kind | Serves | Default port |
|---|---|---|---|
| [Ollama](https://ollama.com/download) | `OLLAMA` | chat, embeddings; the executor can pull models onto it | 11434 |
| [llama-server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server) | `LLAMA_SERVER` | chat, or embeddings with `--embeddings` | 9931 / 8080 |
| [vLLM](https://docs.vllm.ai) | `VLLM` | chat, embeddings, transcription | 8000 |
| [speaches](https://speaches.ai/) | `OPEN_AI_AUDIO` | transcription, speech | 8000 |
| OpenAI | `OPEN_AI` | everything | |
| Anthropic | `ANTHROPIC` | chat | |
| any other `/v1/models` server | `OPEN_AI_COMPATIBLE` | what it lists | |

GPU acceleration is the model server's: run Ollama, vLLM or speaches with the GPU, the executor needs nothing for it.

### Endpoints from the SDK

```typescript
import { Ad4mClient } from '@coasys/ad4m';

const client = new Ad4mClient(executorUrl, token);

// Model servers on this machine's loopback ports. Nothing is saved.
const detected = await client.ai.detectEndpoints();

// Save one. The executor lists its models once first and answers with its health.
const ollama = await client.ai.addEndpoint({
  name: "ollama",
  kind: "OLLAMA",
  baseUrl: "http://127.0.0.1:11434",
});

// A remote API with a key. A key is never sent over plain HTTP except to loopback,
// and never read back (`hasApiKey` says whether one is set).
const openai = await client.ai.addEndpoint({
  name: "openai",
  kind: "OPEN_AI",
  baseUrl: "https://api.openai.com/v1",
  apiKey: process.env.OPENAI_API_KEY,
});

// What a saved endpoint, or a server not saved yet, serves.
const models = await client.ai.discoverModels({ endpointId: ollama.id });
const before = await client.ai.discoverModels({ kind: "OLLAMA", baseUrl: "http://127.0.0.1:11434" });

// Ollama only: download a model onto the server. Progress arrives as `model-status` events.
await client.ai.pullModel(ollama.id, "qwen3:8b");
```

`ai.endpoints`, `ai.addEndpoint`, `ai.updateEndpoint`, `ai.removeEndpoint`, `ai.detectEndpoints`, `ai.pullModel` and `ai.deleteUpstreamModel` are the operator's: a managed user's session is refused. Users read models (name, type, status), not endpoint URLs.

### Headless executors

The executor config file can declare endpoints, models and defaults, applied at start (see [executor configuration](/developer-guides/executor-config)):

```json
{
  "ai_endpoints": [
    { "name": "ollama", "kind": "OLLAMA", "base_url": "http://127.0.0.1:11434" },
    { "name": "speaches", "kind": "OPEN_AI_AUDIO", "base_url": "http://127.0.0.1:8000" }
  ],
  "ai_models": [
    { "name": "qwen", "model_type": "LLM", "endpoint": "ollama", "remote_model": "qwen3:8b" },
    { "name": "nomic", "model_type": "EMBEDDING", "endpoint": "ollama", "remote_model": "nomic-embed-text" },
    { "name": "whisper", "model_type": "TRANSCRIPTION", "endpoint": "speaches", "remote_model": "Systran/faster-whisper-small" }
  ],
  "ai_defaults": { "llm": "qwen", "embedding": "nomic", "transcription": "whisper" }
}
```

The Docker image reads `AD4M_AI_OLLAMA_URL`, `AD4M_AI_LLM_MODEL`, `AD4M_AI_EMBEDDING_MODEL`, `AD4M_AI_TRANSCRIPTION_URL` and `AD4M_AI_TRANSCRIPTION_MODEL`; `docker/compose.ai.yml` runs it with Ollama and speaches.

## Using AI in Your Application

### 1. Adding Models

```typescript
const modelId = await client.ai.addModel({
  name: "qwen",
  modelType: "LLM",
  endpointId: ollama.id,
  remoteModel: "qwen3:8b",
});
await client.ai.setDefaultModel("LLM", modelId);

// Where it stands by its endpoint's last health check:
// READY, MISSING (the endpoint does not list it), ENDPOINT_DOWN, PULLING, UNKNOWN.
const { state } = await client.ai.modelStatus(modelId);
```

`nativeTools` says whether prompts with tools send them as tool definitions. Left out it is on for Ollama and Anthropic and off for an OpenAI-shaped server, where tool support depends on the model and the server's flags (llama-server `--jinja`, vLLM `--enable-auto-tool-choice`); with it off the executor renders the tools into the prompt and reads the calls back from the text.

### 2. Creating AI Tasks

Tasks allow you to define specific use cases with system prompts and examples:

```typescript
const task = await client.ai.addTask(
  "code-helper",
  modelId,
  "You are a helpful coding assistant. Provide clear and concise code examples.",
  [
    { 
      input: "How do I read a file in Node.js?", 
      output: "Here's a simple example using fs.readFile:\n\n```javascript\nconst fs = require('fs');\n\nfs.readFile('file.txt', 'utf8', (err, data) => {\n  if (err) throw err;\n  console.log(data);\n});\n```" 
    }
  ]
);
```

### 3. Using Models

#### Text Generation (LLM)

```typescript
// Using a task
const response = await client.ai.prompt(
  task.taskId,
  "How do I create a web server in Node.js?"
);

// The response will follow the system prompt and examples pattern
console.log(response);
```

#### Text Embeddings

```typescript
// Get vector representation of text, with an embedding model by id or name
const vector = await client.ai.embed("nomic", "Convert this text to a vector");
```

#### Speech-to-Text

```typescript
// Open a transcription stream on a TRANSCRIPTION model
const streamId = await client.ai.openTranscriptionStream(
  transcriptionModelId,
  (text) => {
    console.log("Transcribed:", text);
  }
);

// Feed one utterance at a time (Float32Array samples at 16kHz)
await client.ai.feedTranscriptionStream(streamId, utteranceSamples);

// Close stream when done
await client.ai.closeTranscriptionStream(streamId);
```

The executor does no voice-activity detection: the caller decides where an utterance
starts and ends (for example with an energy gate in an audio worklet) and feeds each one
as it ends. Each utterance goes to the model's endpoint (any server with an OpenAI-shaped
`POST /v1/audio/transcriptions`: speaches, vLLM, a Parakeet wrapper, OpenAI) as one
request; `feedTranscriptionStream` resolves once the text is published, in the order the
utterances were fed, and rejects when the endpoint failed.

Note: Transcription streams are automatically cleaned up after 30 seconds of inactivity.

## Best Practices

1. **Model Selection**
   - A 4-8B instruct model with tool calling covers interpretation and agents on a desktop
   - Use larger models, or a remote API, when quality is critical
   - `faster-whisper-small` transcribes faster than real time on a CPU; `large-v3-turbo` is more accurate

2. **Task Design**
   - Write clear system prompts
   - Provide specific examples
   - Use task-specific models when possible

3. **Resource Management**
   - Close transcription streams when done
   - Check `modelStatus` (or the `model-status` and `ai-endpoint-status` events) before relying on a model
   - Handle errors appropriately

## Error Handling

```typescript
try {
  const response = await client.ai.prompt(taskId, prompt);
} catch (error) {
  if (error.message.includes("is loaded")) {
    // The task's model is gone, or its endpoint could not be used
  } else if (error.message.includes("Task not found")) {
    // Handle missing task
  } else {
    // The endpoint's own error (unreachable, refused key, missing model)
  }
}
```

## Advanced Features

### Default Models

You can set default models for each type:

```typescript
await client.ai.setDefaultModel("LLM", modelId);

// Use default model in tasks
const task = await client.ai.addTask(
  "default-task",
  "default",  // Uses the default LLM
  "System prompt...",
  []
);
```

### Model Updates

Models can be updated while maintaining tasks; the model's client is rebuilt from its endpoint:

```typescript
const updated = await client.ai.updateModel(modelId, {
  name: "qwen",
  modelType: "LLM",
  endpointId: ollama.id,
  remoteModel: "qwen3:14b",
});
```

### Multiple Transcription Streams

You can process the same audio through multiple models simultaneously:

```typescript
// A fast model for a live preview, a more accurate one for the final text
const fastStreamId = await client.ai.openTranscriptionStream(fastModelId, (text) =>
  console.log("Preview:", text)
);
const accurateStreamId = await client.ai.openTranscriptionStream(accurateModelId, (text) =>
  console.log("Final:", text)
);

// Feed audio to both streams efficiently
await client.ai.feedTranscriptionStream([fastStreamId, accurateStreamId], audioSamples);
```

### Automatic Stream Cleanup

Transcription streams are automatically cleaned up after 30 seconds of inactivity to prevent resource leaks. This means:
- No need to manually close streams if the client disconnects
- Resources are freed automatically when streams are abandoned
- Streams remain active as long as they receive audio data regularly

### Pending Interpretation Overlays

When the interpretation engine would overwrite a value a human wrote, it stages
the model's value as an *interpretation overlay* instead of applying it. The
overlay waits until a human accepts or rejects it:

```typescript
const overlays = await perspective.interpretationOverlays();
for (const o of overlays) {
  // o.base: the instance, o.kind: whether the model created the instance
  // or proposed changes to an existing one (see the note below),
  // o.inferred: [realPredicate, stagedValue] pairs
  console.log(o.base, o.kind, o.inferred);
}

await perspective.acceptInterpretation(base);          // the whole overlay
await perspective.rejectInterpretation(base, "soa://title"); // one property
```

`o.kind` is `"create"` or `"update"`, whichever way the overlay was written.

`interpretationOverlays()` always reads from the executor: the list reflects the
executor's state at the time of the request, and nothing is cached after it
returns. When several callers ask at the same time (for example, many components
rendering after a sync burst), they share one request, and each caller gets its
own copy of the array. A call made after that request has finished sends a new
one. `acceptInterpretation()` and `rejectInterpretation()` detach a request
that is still running, so a call made after they resolve sends a new request
rather than joining one that started before the write. Nothing is cached, so
there is no cache to invalidate.
