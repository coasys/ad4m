# Executor config file

`ad4m-executor run` can read its settings from a JSON file instead of flags,
so a headless executor (a systemd service, a container) keeps them in one
place and restarts with the same settings. The keys are the ones the ADAM
Launcher writes to `~/.ad4m/launcher-state.json`.

```bash
ad4m-executor run --config /etc/ad4m/executor-config.json
# or
AD4M_CONFIG=/etc/ad4m/executor-config.json ad4m-executor run
```

There is no default path: without `--config` (or `AD4M_CONFIG`), `run`
behaves as before and uses only flags and environment variables.

## Precedence

Each setting is taken from the last of these that sets it:

1. the config file,
2. an `AD4M_<FLAG>` environment variable,
3. the flag.

`ad4m-executor config print` takes the same flags and prints the merged
result as JSON, with every secret replaced by `"<redacted>"` (an unset
secret shows as `null`):

```bash
ad4m-executor config print --config /etc/ad4m/executor-config.json --port 12400
```

## Keys

Every key is optional. The file is rejected at startup if it contains a key
not listed here, at any depth (a typo fails loudly instead of being
ignored, and the error names the key by its path, e.g.
`multi_user_config.tls_config.tls_prot`), or a secret value (see
[Secrets](#secrets)).

| Key | Type | Default | Flag / variable |
|---|---|---|---|
| `app_data_path` | string | `~/.ad4m` | `--app-data-path` / `AD4M_APP_DATA_PATH` |
| `port` | number | `12000` | `--port` / `AD4M_PORT` |
| `public_origins` | list of origins | none: only this executor's loopback origins as a key statement's audience — and none on a network listener, so key login is refused there | `--public-origin` (repeat it, or separate with `,`) / `AD4M_PUBLIC_ORIGINS` |
| `hc_admin_port` | number | first free from 2000 | `--hc-admin-port` / `AD4M_HC_ADMIN_PORT` |
| `hc_app_port` | number | first free from 1337 | `--hc-app-port` / `AD4M_HC_APP_PORT` |
| `localhost` | bool | `true` | `--localhost` / `AD4M_LOCALHOST` |
| `run_dapp_server` | bool | `true` (port 8080) | `--run-dapp-server` / `AD4M_RUN_DAPP_SERVER` |
| `auto_permit_cap_requests` | bool | `false` with a config file, `true` without | `--auto-permit-cap-requests` / `AD4M_AUTO_PERMIT_CAP_REQUESTS` |
| `mcp_enabled` | bool | `false` | `--enable-mcp` / `AD4M_ENABLE_MCP` |
| `mcp_port` | number | `3001` | `--mcp-port` / `AD4M_MCP_PORT` |
| `sfu_bind_addr` | string (IP) | `127.0.0.1`; the outbound interface with `localhost: false` | `--sfu-bind-addr` / `AD4M_SFU_BIND_ADDR` |
| `sfu_udp_port` | number | a free port, new at each start | `--sfu-udp-port` / `AD4M_SFU_UDP_PORT` |
| `sfu_public_addr` | string (IP) | the STUN probe's address | `--sfu-public-addr` / `AD4M_SFU_PUBLIC_ADDR` |
| `sfu_stun_server` | string (`host:port`) | no probe | `--sfu-stun-server` / `AD4M_SFU_STUN_SERVER` |
| `log_config` | object: crate → level | see below | `RUST_LOG` overrides it |
| `log_dir` | string (folder) | stdout | `--log-dir` / `AD4M_LOG_DIR` |
| `multi_user_config.enabled` | bool | `false` | `--enable-multi-user` / `AD4M_ENABLE_MULTI_USER` |
| `multi_user_config.tls_config` | object or `null` | no TLS | see below |
| `multi_user_config.smtp_config` | object or `null` | no email | see below |

Inside the nested objects some keys are required: `enabled` in
`multi_user_config`; `enabled`, `cert_file_path` and `key_file_path` in
`tls_config`; every key but `password_file` in `smtp_config`.
`tls_config` and `smtp_config` may be `null` or left out.

A string value that is empty or only whitespace (`"app_data_path": ""`)
stops `run` with an error that names the key
(`` `app_data_path` is empty or only whitespace ``). Leave an optional key
out to get its default.

`multi_user_config.enabled: false` (or `--enable-multi-user false`) does not
turn multi-user off on a data directory where it was enabled before: the
executor records multi-user as on in its database and only ever sets it.

Multi-user mode needs an admin credential. Without one, a caller with no
token on a loopback listener is the operator, who could act as every user:
`run` refuses `multi_user_config.enabled: true` (and a data directory whose
database has multi-user on) when no admin credential is set, even with
`--insecure-no-admin-credential`, and `user.setMultiUserEnabled(true)`
answers 403.

**`tls_config`** starts an HTTPS/WSS listener on `0.0.0.0:<tls_port>`. The
plain RPC port then stays on `127.0.0.1`.

```json
{ "enabled": true, "cert_file_path": "/etc/ad4m/tls/cert.pem",
  "key_file_path": "/etc/ad4m/tls/key.pem", "tls_port": null }
```

`tls_port: null` means `port + 1`. The flags `--tls-cert-file`,
`--tls-key-file` and `--tls-port` (`AD4M_TLS_CERT_FILE`, `AD4M_TLS_KEY_FILE`,
`AD4M_TLS_PORT`) override the file's values; giving a certificate or key
flag turns TLS on, and TLS without both a certificate and a key stops `run`.

**`smtp_config`** is the account multi-user verification emails are sent from.

```json
{ "enabled": true, "host": "smtp.example.org", "port": 465,
  "username": "ad4m@example.org", "from_address": "ad4m@example.org",
  "password_file": "/etc/ad4m/secrets/smtp-password" }
```

With `enabled: true`, `run` stops unless a password is set (see
[Secrets](#secrets)).

**The `sfu_*` keys** decide where callers send media. The SFU binds
`sfu_bind_addr` on `sfu_udp_port` and offers that address to every caller.
On a machine behind NAT, set `sfu_bind_addr` to its LAN address, fix
`sfu_udp_port` and forward that UDP port on the router: the SFU then also
offers its public address on that port, which callers outside the LAN reach.
The public address is `sfu_public_addr` if set (it needs `sfu_udp_port`),
otherwise the address the `sfu_stun_server` reports, asked once at startup. `sfu.status` reports
`isPublic: true` once the STUN server sees the public address the SFU offers.
A fixed port that is taken stops `run`. The public address is read at
startup only: after the public IP changes, restart the executor.

```json
{ "sfu_bind_addr": "192.168.0.10", "sfu_udp_port": 40000,
  "sfu_stun_server": "stun.l.google.com:19302" }
```

**`identity`** (`storeUrl`, `storeKeys`, `allowPrivateSrc`; flags
`--identity-store-url`, `--identity-store-keys`) names the `did:scid`
identity store and the keys its signed heads must carry. Leave both out to
use the store of the executor's network: the `identityStore` of the seed
`ad4m-executor init` writes into the data folder (the seed this build
carries names `https://store.ad4m.dev`; `--network-bootstrap-seed` gives
another network's seed, whose `identityStore` names that network's store). A
seed without `identityStore`, such as one an older `init` wrote, uses the
store of the seed this build carries, so an upgraded executor keeps its store
without re-running `init`. With no store at all, `did:scid` identities are
off: `identity.status` answers `store: null`, and `identity.publish` /
`identity.claimOffer` refuse `no-store-keys`. A `storeUrl` without
`storeKeys` trusts no key for it. Errors and warnings about the store name
where the bad value came from: `identity.storeUrl` / `identity.storeKeys`, or
the seed's `identityStore`.

```json
{ "identity": { "storeUrl": "https://store.example.org",
  "storeKeys": ["z6Mk…"] } }
```

**`public_origins`** lists the origins (`scheme://host[:port]`) clients reach
this executor at, such as `["https://ad4m.example.org"]`. A key login
(`user.loginWithKey`, `user.renewSession`) signs the origin the client dialed
into its statement, and the executor accepts the statement only when that
origin, normalised (`wss` reads as `https`, `ws` as `http`, the host in lower
case, a default port left out), is one of these. So a server that passes this
executor's challenge on to a person's app gets a statement for its own origin,
which this executor refuses. Without `public_origins` a loopback-only executor
accepts only its own loopback origins (`http://127.0.0.1:<port>`,
`http://localhost:<port>`, `http://[::1]:<port>`), and refuses a statement for
any other origin with 403 `no-public-origin`. The check restricts the signed
audience, not the caller's location: a remote key holder can sign a loopback
audience just as easily as any other, so on a listener the network reaches (TLS,
or `localhost` off) without `public_origins` no origin is accepted at all and
key login is refused outright — `user.sessionChallenge`, `user.loginWithKey`
and `user.renewSession` answer 403 `no-audience`, which names the setting.
Set `public_origins` there to pin key logins to origins the operator names. Once the key is set, only the listed origins count: list a
loopback origin too if local apps log in with a key. The executor never reads
the origin from the connection's `Host` or `Origin` header, which a caller
chooses. A value that is not an origin (a path, a query, no host) stops the
start with an error that names `public_origins`.

`user.sessionChallenge` counts open challenges by the address the caller
connects from: at most 100 per address. The executor does not read forwarding
headers for this. Behind a reverse proxy every caller connects from the proxy,
so all of them share the proxy's budget. Callers without connect info share one
budget too. Rate-limit `user.sessionChallenge` at the proxy. A key session's
renewal does not draw from this budget: each key session has its own slot.

**`log_config`** sets a level (`error`, `warn`, `info`, `debug`, `trace`)
per crate over the defaults `rust_executor: info`, `holochain: warn`,
`wasmer_compiler_cranelift: warn`, `warp::server: info`.

Settings with no config key are flags only, each with its
`AD4M_<FLAG>` variable: `--network-bootstrap-seed`,
`--language-language-only`, `--connect-holochain`, `--run-holochain`,
`--hc-use-bootstrap`, `--hc-use-local-proxy`, `--hc-use-mdns`,
`--hc-use-proxy`, `--hc-proxy-url`, `--hc-bootstrap-url`, `--hc-relay-url`,
`--log-holochain-metrics`, `--dynamic-class-tools`, `--pid-file`,
`--watch-stdin`, `--custody-channel`, `--exit-with-parent`,
`--insecure-no-admin-credential`.

`--exit-with-parent` (`AD4M_EXIT_WITH_PARENT=true`) is for launchers and test
harnesses: the executor shuts down once the process that started it is gone,
however that process ended, so a launcher that crashes or is killed leaves no
executor behind. Off by default, so an executor started in the background from
a shell keeps running after the shell exits. Linux and macOS only: on Windows
the setting is accepted and has no effect. Its stop exits with 0, as the run
contract's other stops do.
The variable name is the flag in upper case with `-` as `_`, prefixed with
`AD4M_`: `--hc-relay-url` reads `AD4M_HC_RELAY_URL`.

A variable that is set but empty or only whitespace stops `run` with an
error that names it (`AD4M_APP_DATA_PATH is set but empty or only
whitespace`), and so does such a flag value.
Neither is laid over the file: `AD4M_APP_DATA_PATH=${DATA_DIR}` with
`DATA_DIR` unset would otherwise put the data directory under the working
directory. Unset the variable to use the file's value.

## Changing the file while the executor runs

`runtime.config` (operator) returns the file's values, every key with its
class, and `restartPending`. `runtime.setConfig { set, unset }` (operator)
writes keys to the file the executor started with; without `--config` it
answers 409 `no-config-file`. It writes a temporary file in the same folder,
mode 0600, then renames it over the file, and keeps the keys it does not
change. Every written key takes effect at the next start
(`restartPending: true`); `runtime.restart` answers, then exits 75 so the
supervisor starts the executor again. The answer lists each key it did not
write, with a reason:

| Reason | When |
|---|---|
| `local-only` | a `machine` key from a caller that is not the operator on this machine (the admin credential on a loopback listener) |
| `pinned-by-config` | a flag or an `AD4M_*` variable sets the key at this start, so a write would not take effect |
| `invalid` | the value would stop the next start, or the key's validator refused it (`detail` says why) |
| `unknown-key` | no such key |

`restart` keys: `mcp_enabled`, `mcp_port`, `log_config`,
`auto_permit_cap_requests`. Every other key is a `machine` key: paths,
listeners, ports, `public_origins`, `multi_user_config`, `identity`, `log_dir`. A write
publishes `config-changed` to the operator.

## Running under a supervisor

A supervisor (the desktop app, systemd, a host) reads the exit code:

| Code | Meaning | What the supervisor does |
|---|---|---|
| 0 | stopped: `runtime.quit`, SIGTERM, SIGINT, or stdin closed with `--watch-stdin true` | nothing |
| 75 | `runtime.restart` | start the executor again with the same arguments |
| 78 | the config or a flag is refused (also `--custody-channel` with multi-user mode, without a custody credential on the first line of stdin, or with `AD4M_CUSTODY_CREDENTIAL` set) | do not retry: it fails the same way |
| 79 | another executor holds this data folder (`<app_data_path>/executor.lock`) | report it |
| 80 | the API port does not bind | pick another port and start again |
| other, or a signal | a crash | restart with a delay |

- **Readiness**: `GET /health` answers `{"status":"ok"}` once the API
  listens, the last step of a start.
- **`--watch-stdin true`**: the executor stops gracefully when its stdin
  reaches its end. The supervisor holds the pipe's write end and never
  writes, so the executor never outlives the supervisor.
- **The admin credential**: pass it in the environment
  (`AD4M_ADMIN_CREDENTIAL`, or `AD4M_ADMIN_CREDENTIAL_FILE`), never on the
  command line, and give a new one at each start.
- **`--log-dir <folder>`** (`log_dir`): the log goes to
  `<folder>/executor-0.log`; the five newest runs stay (`executor-1.log` is
  the run before), and a file stops at 50 MiB. `runtime.logTail { lines }`
  (operator, at most 2000) returns its newest lines.
- **`--custody-channel`**: this executor serves the custody channel
  (`identity.custodyStatus`, `identity.takeMaster`, and `identity.inboxAck`,
  which with the channel on only the custody service may call) to the custody
  credential on a loopback listener only. The custody credential is a second
  secret, given only to the custody service. It is not an operator: on a
  network listener it opens no session at all, and on a loopback listener it
  reaches only the identity calls the custody service makes (no
  `runtime.setConfig`, `agent.lock` or `identity.rekey`: 403
  `not-a-custody-call`). The supervisor writes it as the
  **first line of the executor's stdin** (the value, then `\n`; a trailing
  `\r` is dropped), right after it starts the executor; the executor reads
  that line before anything else, keeps the value in memory only, and wipes
  it when it is dropped. Then the supervisor keeps the pipe open and writes
  nothing more (with `--watch-stdin true` the executor stops when it
  closes; without it, closing does nothing). Generate a new credential at
  each start.

  Not the environment and not a flag: a process's environment is a file
  others can read (`/proc/<pid>/environ` on Linux; same-user processes on
  macOS too), so is its command line, and the admin credential, which an
  app's window may hold, reads host files. `AD4M_CUSTODY_CREDENTIAL` or
  `AD4M_CUSTODY_CREDENTIAL_FILE` set stops `run` with 78, as does stdin
  ending before the line, an empty line, or the admin credential's value.
  The admin credential gets 403 `no-custody-channel`. Multi-user mode
  refuses the channel too: `run` exits 78, and
  `user.setMultiUserEnabled(true)` answers 403.
- **Local only**: `runtime.quit`, `runtime.restart`, `agent.unlock`,
  `agent.signSessionStatement`, `identity.rekey` and `identity.custodyStatus`
  answer only the operator on a loopback listener.
  A caller without the admin credential gets 403 `Admin credential required`;
  the admin credential on a network listener gets 403 `local-only`.
  `runtime.setConfig` from such a caller writes the other keys and lists each
  `machine` key in `refused` with the reason `local-only` (the table above).
  A listener is loopback by the address it binds, not by the
  address a caller connects from: on `--localhost false` without TLS the
  executor binds 0.0.0.0, has no loopback listener, and these calls answer
  no one. A request with a `Forwarded`, `X-Forwarded-For` or `X-Real-IP`
  header counts as network, even on a loopback listener. So these calls
  refuse through a proxy such as nginx, Caddy or cloudflared. A raw TCP
  forward (`ssh -R`) sets none of these headers and still counts as
  loopback. Only the admin credential guards that case. On an executor with
  no admin credential (`--insecure-no-admin-credential`), a loopback connection without a token
  is the operator, and the WebSocket endpoint does not check `Origin`: a web
  page in a browser on the same machine can reach these methods. Run with an
  admin credential. An operator who logged in with a device key is never on
  this machine, so these refuse it too. Creating, importing or locking the
  agent and exporting or importing data (`agent.generate`, `agent.import`,
  `agent.lock`, `runtime.exportData`, `runtime.importData`) are not local
  only: a remote operator may move the whole data folder.
- **`ad4m-executor rekey`**: gives the executor a new main wallet key, so a
  revoked server links again. Run it on the server itself: it calls
  `identity.rekey` on a loopback address with the admin credential from
  `AD4M_ADMIN_CREDENTIAL_FILE` (or `--admin-credential`,
  `AD4M_ADMIN_CREDENTIAL`). Tokens signed with the old key stop working, so
  apps ask for access again. With the local wallet, the old key signed every
  token, so the apps of managed users ask again too.

## Secrets

The config file never holds a secret value. An `admin_credential` key or a
`smtp_config.password` key stops `run` with an error that names the key.
Secrets come from files or environment variables:

| Secret | From a file | From a value | In the config file |
|---|---|---|---|
| Admin credential | `AD4M_ADMIN_CREDENTIAL_FILE` | `AD4M_ADMIN_CREDENTIAL` | — |
| SMTP password | `AD4M_SMTP_PASSWORD_FILE` | `AD4M_SMTP_PASSWORD` | `smtp_config.password_file` |
| Agent passphrase | `AD4M_UNLOCK_PASSPHRASE_FILE` | — | — |

- Setting both variables of one secret stops `run`. The variables win over
  `smtp_config.password_file`.
- The custody credential (`--custody-channel`) comes from none of these: only
  from the first line of stdin (see [Running under a supervisor](#running-under-a-supervisor)).
  A `custody_credential` key in the config file stops `run`, and so does
  `AD4M_CUSTODY_CREDENTIAL` or `AD4M_CUSTODY_CREDENTIAL_FILE`.
- A secret file must not be readable by group or others: mode `0600` or
  `0400`, otherwise `run` stops and names the file and its mode.
- One trailing newline is removed, so `echo "$SECRET" > file` works.
- An empty secret stops `run`: an empty file (or one holding only a
  newline), an empty `AD4M_ADMIN_CREDENTIAL` or `AD4M_SMTP_PASSWORD`, or
  `--admin-credential ""`. An empty admin credential would match the empty
  token a client without credentials sends.
- `--admin-credential <value>` still works and wins over both variables,
  but the value is visible to every user on the host through `ps`. Prefer
  the file.
- Neither `run`, `config print` nor the executor's log prints a secret
  value, at any log level.

Under systemd, load the files with `LoadCredential=` and point the variables
at the credentials directory:

```ini
LoadCredential=admin-credential:/etc/ad4m/secrets/admin-credential
LoadCredential=unlock-passphrase:/etc/ad4m/secrets/unlock-passphrase
Environment=AD4M_ADMIN_CREDENTIAL_FILE=%d/admin-credential
Environment=AD4M_UNLOCK_PASSPHRASE_FILE=%d/unlock-passphrase
```

### Unlocking at startup

With `AD4M_UNLOCK_PASSPHRASE_FILE` set, the executor unlocks its agent
itself once it has started, as `agent.unlock` would, so a restarted executor
serves requests without anyone unlocking it. It logs
`Agent unlocked at startup` on success. On a wrong passphrase it logs an
error starting `Unlocking the agent at startup … failed`, keeps running
with the agent locked, and waits for `agent.unlock`. If no agent has been
generated yet it logs a warning and does nothing; generate the agent, and
the next start unlocks it.

## Example

```json
{
  "app_data_path": "/var/lib/ad4m",
  "port": 12400,
  "hc_admin_port": 12401,
  "hc_app_port": 12402,
  "run_dapp_server": false,
  "multi_user_config": {
    "enabled": true,
    "tls_config": null,
    "smtp_config": {
      "enabled": true, "host": "smtp.example.org", "port": 465,
      "username": "ad4m@example.org", "from_address": "ad4m@example.org",
      "password_file": "/etc/ad4m/secrets/smtp-password"
    }
  },
  "log_config": { "rust_executor": "info", "holochain": "warn" },
  "mcp_enabled": true,
  "mcp_port": 3003
}
```

```bash
AD4M_ADMIN_CREDENTIAL_FILE=/etc/ad4m/secrets/admin-credential \
AD4M_UNLOCK_PASSPHRASE_FILE=/etc/ad4m/secrets/unlock-passphrase \
  ad4m-executor run --config /etc/ad4m/executor-config.json
```
