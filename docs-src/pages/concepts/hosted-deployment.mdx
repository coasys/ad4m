# Hosted deployment

What changes when the executor is hosted? One executor process serves many agents. Each user gets a DID of their own and sees only their own perspectives; the model API an app uses is the same as on a local executor. What differs is the connection, the authentication and who operates the machine.

## The example: a user on a hosted executor

```typescript
import { getAd4mClient } from "@coasys/ad4m-connect";

const ad4m = await getAd4mClient({
  appInfo: { name: "Team board", description: "Tasks for the team", url: "board.example.com" },
  capabilities: [{ with: { domain: "*", pointers: ["*"] }, can: ["*"] }],
  hosting: true,                                 // offer "Remote Node" next to "Local Node"
  remoteUrl: "https://ad4m.example.com:12001",   // pre-fills the host URL field
});

const me = await ad4m.agent.me();                // this user's own DID
const board = await ad4m.perspective.add("Board"); // owned by this user
```

The user picks "Remote Node", browses the hosting index or types a URL, enters an email address, and then either a password or a code from their inbox. From then on `ad4m` is an ordinary `Ad4mClient` on `wss://ad4m.example.com:12001/api/v1/ws` with a JWT for that user.

The same steps without the dialog, in Node or a test:

```typescript
import { Ad4mClient } from "@coasys/ad4m";

const anon = new Ad4mClient("https://ad4m.example.com:12001");
const created = await anon.agent.createUser("alice@example.com", "a long password");
// { did: "did:key:z6Mk…", success: true }   or   { did: "", success: false, error: "…" }
const token = await anon.agent.loginUser("alice@example.com", "a long password");
const ad4m = new Ad4mClient("https://ad4m.example.com:12001", token);
```

## The picture

```text
                 one host, one executor process
   ┌───────────────────────────────────────────────────────────┐
   │ main agent (the operator)     admin credential            │
   │ wallet: main key + one key per user (did:key:…)           │
   │                                                           │
   │  alice@…  ──▶ did:key:A ──▶ perspectives owned by A       │
   │  bob@…    ──▶ did:key:B ──▶ perspectives owned by B       │
   │  shared:  neighbourhood X ── one perspective, owners [A,B]│
   │                                                           │
   │  RPC  http://127.0.0.1:12000       (local apps, Launcher) │
   │  RPC  https://0.0.0.0:12001        (remote users, TLS)    │
   │  MCP  :3001 / :3002 (TLS)          (agents)               │
   └───────────────────────────────────────────────────────────┘
```

## Who holds the keys

On a hosted executor **the host holds every user's signing key**. `createUser` makes a new key in the executor's wallet, named by its DID, saves the wallet and records the email with a password hash (`rust-executor/src/user_management.rs`, `create_user`). Links and expressions the user writes are signed with that key, by the executor, as on a local node. The user owns a DID; the operator runs the machine that can sign as it.

The wallet is locked after every restart until the operator unlocks it. While it is locked, sign-up and login fail with "Executor is locked … ask the executor operator to call unlockAgent". With the `shared` wallet backend the keys live in an external wallet service instead of the executor process (`wallet_backend` in `rust-executor/src/config.rs`).

Choose a host you trust as you would an email provider, or run your own executor: [Run an executor](../start/run-an-executor.mdx).

## Signing up and logging in

| Step | SDK call | What happens |
|---|---|---|
| Is this a hosted node? | `runtime.multiUserEnabled()` | Readable without a token |
| Sign up | `agent.createUser(email, password)` | New key and DID; a six-digit code is emailed when SMTP is configured. Returns `UserCreationResult` `{ did, success, error? }`. An existing email with the right password returns that user's DID |
| Log in with a password | `agent.loginUser(email, password)` | Returns the JWT |
| Log in by email code | `agent.requestLoginVerification(email, appInfo?)` then `agent.verifyEmailCode(email, code, "login")` | The first call sends a code to a known email if SMTP is configured and returns `{ success, message, requiresPassword, isExistingUser }`; without SMTP, or for an unknown email, it answers `requiresPassword: true`. `verifyEmailCode` returns the JWT |
| Guest | `connectAsGuest(options, hostUrl)` from `@coasys/ad4m-connect` | Random `guest-…@flux.demo` account, credentials kept in `localStorage` for that host |

`@coasys/ad4m-connect` runs this table for you: an email it does not know asks for a password and creates the account; a known email gets a code when the host has SMTP, a password field when it does not (`connect/src/core.ts`, `components/views/RemoteAuthentication.ts`). Emails are trimmed and lowercased by the executor.

Before login a caller with no token may only request a capability, read whether multi-user mode is on, and sign up, log in and verify when it is (`anonymous_capabilities`, `rust-executor/src/agent/capabilities/mod.rs`). It cannot list users.

## What a user token may do

The JWT a login returns carries the executor's **default user capability set**, whatever the app listed in `capabilities` (`get_user_default_capabilities`, `rust-executor/src/agent/capabilities/defs.rs`). It covers perspectives, neighbourhoods, languages, expressions, the user's own agent, friends and messages, hosting info and AI prompting and transcription. It leaves out `agent` `LOCK`/`UNLOCK`/`PERMIT`, `runtime` `QUIT`, AI model management (`UPDATE`/`DELETE`) and listing users. The domain table is on [Agent, executor and capabilities](./agent-executor-capabilities.mdx#reference-domains-and-verbs).

On top of capabilities, calls that act on the node itself (the main agent's identity, wallet, files or executor-wide settings) refuse a user session outright (`rust-executor/src/api/guards.rs`). Turning multi-user mode on and off and granting a user free access need the admin credential.

## Data isolation

- **Perspectives are owned.** A perspective a user creates is owned by their DID. A user session reaches only perspectives it owns; an app session on the main agent reaches unowned ones and the main agent's own (`can_access_perspective`, `rust-executor/src/helpers.rs`). The admin credential lists every perspective on the executor (`list_perspectives`, `rust-executor/src/api/perspectives_ws.rs`): isolation is between users, not from the operator.
- **Neighbourhoods are shared within the host.** When two users of one host join the same neighbourhood, the executor keeps one perspective and adds the second user to its owners (`install_neighbourhood_with_context`, `rust-executor/src/neighbourhoods.rs`). Links each user writes are signed with their own key.

<Callout type="warning">
  Removing a neighbourhood perspective removes it for every owner on that host: `perspective.remove` deletes the one shared copy, not one user's membership (`delete_perspective`, `rust-executor/src/api/perspectives_ws.rs`).
</Callout>

## Paid and free hosting

Hosting is free by default (`runtime.freeHostingEnabled()` is `true` until the operator changes it). With paid hosting on, a user without free access needs compute credits: link writes and AI calls check and deduct them, and a user at zero gets "Insufficient compute credits" (`check_credits`, `rust-executor/src/api/perspectives_ws.rs`). `agent.hostingUserInfo()` returns the user's `{ email, remainingCredits, hotWalletAddress?, freeAccess }`; `@coasys/ad4m-connect` shows the balance and a top-up dialog. Payment is in wHOT through the Unyt Holochain app; registering a host with the hosting index and pricing are set in the Launcher's Hosting view.

## Agents on a hosted executor

The MCP server serves hosted users too. An agent connects to the MCP port (or to `mcp_port + 1` over TLS, with the RPC port's certificate) and authenticates with the `signup`, `login_email`, `request_login_verification` and `verify_email_code` tools instead of `request_capability` (`rust-executor/src/mcp/tools/auth.rs`, `mcp/server.rs`). The session then acts as that user. See [Run the MCP server](../how-to/mcp-server.mdx).

## How it is built

Sign-up and login are in `rust-executor/src/user_management.rs` and the `user.*` RPC methods in `rust-executor/src/api/users_ws.rs`; capabilities for anonymous callers and user tokens are in `rust-executor/src/agent/capabilities/`; the listeners (cleartext on 127.0.0.1, TLS on 0.0.0.0) are bound in `bind_api_listeners`, `rust-executor/src/api/mod.rs`. The browser side is `connect/src/core.ts`.
